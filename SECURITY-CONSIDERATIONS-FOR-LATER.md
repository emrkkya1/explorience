# Security Considerations For Later

This file tracks known security gaps deferred during early iteration. Append concise entries as you discover them.

## Explored POI verification

- **Attestation gap (thick-client trust).** Explored state is set by a client-side LLM call with no server verification. Malicious players can UPDATE `poi_discoveries.explored=TRUE` directly via the Supabase client. Later: gate the flip via an RPC that records an LLM response transcript / signed payload, or move the LLM call server-side (Supabase Edge Function) so the client never holds the trust decision.
- **Loose `explored_by` UPDATE policy.** `016_add_poi_update_policies.sql` permits any game member to UPDATE `poi_discoveries` rows, including setting `explored_by` to any `player_id`. Tighten the WITH CHECK to require `explored_by = auth.player_id` (or NULL).
- **Plaintext LLM API key in AsyncStorage.** Acceptable for early iteration; consider the OS keystore (Keychain/Keystore via `expo-secure-store`) before public release. The key currently ships in the JS bundle when set via `EXPO_PUBLIC_*` env vars.
- **User verification photos are public-readable.** Objects in the `poi_explores` bucket are world-readable to anyone with the URL. Fine for nostalgia display; not appropriate if photos ever contain PII scenes. Consider signed URLs or auth-gated reads later.
- **No rate limiting on LLM calls.** A malicious player could spam the compare endpoint to burn API quota. Later: throttle client-side (cooldown after N attempts per POI) and/or enforce server-side rate limits in the edge function variant.

## poi_discoveries / poi_hints RLS hardening (migration 019)

- **Client no longer relies on split INSERT/UPDATE policies.** Discovery and explore writes now go through `SECURITY DEFINER` RPCs (`upsert_poi_discovery`, `upsert_poi_hint`) that verify caller-ownership of `player_id` server-side. This removes the brittle client RLS path that surfaced as hard errors during token refresh / replaced-anon-session windows.
- **WITH CHECK ownership tightened.** `poi_discoveries` INSERT/UPDATE policies now require `player_id` to belong to the caller's `auth.uid()`, and `explored_by` (if set) must equal the caller's player row. Closes the loose `explored_by` gap above.

## Background location tracking

- **No raw coordinate persistence.** Background location is processed in-memory and immediately binned to fog cells (bitmap indices); no raw lat/lng is ever sent to Supabase. This extends the §2B invariant to the background path — the `fog_deltas` and `poi_discoveries` rows written from the task are identical in shape to those written from the foreground path; no new tables were introduced.
- **Persistent Android foreground-service notification.** While tracking is active on Android, a visible foreground-service notification ("Explorience — Recording your exploration…") is shown by platform requirement, giving the user ambient awareness. iOS does not show a persistent notification but the location indicator appears in the status bar.
- **POI discovery notifications reveal inferred user activity.** "New discovery! X discovered while you were away" is generated by the task and shown as a local notification. Review whether this disclosure pattern is acceptable for all users (e.g. shared device scenarios) before public release.
- **AsyncStorage now holds `{gameId, playerId, cityId, cityName, bounds, gridWidth, gridHeight}` reachable from the background task scope.** These values were already in AsyncStorage via `sessionStore` — the new `bgTrackingState.ts` adds a parallel mirror used by the task. No new data exposure introduced, but the task can read them at arbitrary times (subject to the same device-level disk-encryption as the OS provides).
- **`bgEventsLedger` stores `poi_id`s of hints and discoveries that occurred while the app was backgrounded, cleared on user dismiss.** No PII — POI coordinates and names are resolved client-side from `poiCache` (itself a server-derived superset).
- **Notification permission is an explicit system-level prompt; user can decline and tracking still works silently** (discovery RPCs continue, no notification visible). Acceptable because the user explicitly enabled bg tracking first; they have already consented to the data flow, the notification is just disclosure.
- **Toggle desync recovery.** If `bg_tracking_enabled=true` but the OS later revokes background permission (user restricted in Settings), the toggle UI surfaces "Permission needed" and offers `Linking.openURL('app-settings:')` — no silent failure. Verifies via `Location.hasStartedLocationUpdatesAsync` on each `useBackgroundTracking` mount.
- **No active session safety.** If the user logs out (`clearActiveSession`) the bg task self-stops on next foreground via `stopBackgroundTracking()` called in the Log Out handler. If the app is killed mid-tracking and re-launched without a session, the task callback reads `getBgTrackingContext() === null` and no-ops; the task stays registered but does zero work, becoming a battery non-issue.
- **Stale POI cache risk.** The task reads POIs from AsyncStorage (`poiCache`) which is only refreshed on `usePois` foreground mount. If a game's POIs are edited server-side while the app is backgrounded for days, the task evaluates proximity against stale coordinates. Mitigation: cache refreshes on next foreground `usePois` mount. Trade-off documented per NFR.

## OpenAI Compatible custom endpoint

- **User-controlled endpoint URL.** The OpenAI Compatible provider allows users to enter any endpoint URL. The API key is sent as a Bearer token to this endpoint. No validation is performed on the endpoint — a malicious or misconfigured URL could intercept the API key or return crafted responses. Later: consider HTTPS-only enforcement, endpoint allowlisting, or warning users about non-HTTPS endpoints.
- **Favicon fetching leaks endpoint origin.** When a user enters an endpoint, the app performs a HEAD request to `{origin}/favicon.ico` to display a favicon. This reveals the endpoint host to the favicon server. Acceptable for early iteration; later: consider making this opt-in or removing it if privacy is a concern.
